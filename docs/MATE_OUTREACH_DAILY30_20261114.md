# MATE営業：合計30通/日モード（2026-11-14）

- 上限: 1日30通（CARE / SPARK / PLAY 各最大10通）、毎時の1回の実行は最大5通。
- 候補取込: 1サイクル最大200件。公式HTTPSとCSV再利用確認、重複排除を継続。
- 返信追跡: 最新の送信済み90件を対象（ただしGAS実行時間に注意）。
- 集計: 送信試行・送信済み・返信あり・配信停止・送信結果要確認を区別。返信率はログが捕捉できた範囲の参考値。

## 送信適格性を維持する理由
送信拡大の承認は、個々の企業が営業メールを受け入れた証拠ではない。送信済み、配信停止、拒否表示、例示用メールアドレス、個人メール、公式サイト確認失敗は保留のまま。公開された業務用メールアドレスには適法性の別途確認が必要。

## 実績の読み方
- `営業送信ログV4` は送信の技術的記録。掲載契約や問い合わせの成立は意味しない。
- `診断` の返信率は「返信あり」の判定が付いた件数の割合であり、商談・掲載申請への転換率ではない。
- 実在事業者の掲載申請を営業成果に結びつけるには、受付IDと事業者・送信先の照合、および内部テスト除外が必要。

## 11/14 追加実装の機能
- `mateV4ReconcileSentReservations`: 送信結果要確認の直近20行について、同一宛先・完全一致件名・送信日時・MATE送信元をGmail送信済みメールに照合。見つかった場合だけ送信済みに確定し、GmailメッセージIDをログに記録。未確認の予約は再送しない。毎時サイクルに組み込み済み。
- `diagnoseMateOutreachApplicationsV4`: 申請台帳から内部テスト・差戻しを除外し、送信後に同じサービス・正規化事業者名で届いた申請数を集計。これは名前照合の相関指標で、営業メールが原因だった証明ではない。
- `diagnoseMateV4Health`: 返信件数、配信停止件数、送信結果要確認件数、参考返信率、実申請の保守的な照合結果を表示。
- Gmail APIおよび台帳上の送信済みを併用し、送信ログの遅延をそのまま未送信扱いにしない。
- 今回の追加コードもGitHubだけでは稼働中のGASに自動反映されない。最新版を再度GASに全文置換して保存する。

## 運用診断
`diagnoseMateV4Health` の `phase` が `DAILY_30`、`dailyCap` が30、`active` がtrueであることを確認する。既存候補が送信可能でなくても設定自体が正しい場合がある。送信済みと保留の件数は必ずGmailの実履歴と突合する。

## 11/14 候補獲得と30通運用の追加強化（GitHub反映済み・GAS再反映待ち）
1. **既存候補の再監査を未送信優先に変更**: `mateV4AuditOfficialContacts` は送信済み・送信結果不明の予約行を監査対象から外し、CARE・SPARK・PLAYをラウンドロビンで巡回する。最新の本人確認・営業拒否・配信停止・公式HTTPS根拠の条件は維持する。
2. **監査件数は標準24件/回**: `MATE_PUBLIC_AUDIT_BATCH` を設定すれば8〜24件の範囲で変更可能。上限はGAS実行時間の制約を考慮したもの。
3. **CAREの自治体候補を収集拡大**: 既存シート `権限移譲区市_営業候補` を、公式URLが存在する事業者の発見元に追加。連絡先メールや公表内容は送信の許可として引き継がず、公式サイト自動監査へ回す。現時点で新規何件が追加されたかは未検証。
4. **Gmail過去送信チェックの長期運用対策**: 過去の手動送信を固定期間で確認し、最近7日の送信履歴を別途照合。過去の送信予約・実送信ログは台帳全体で永久に抑止する。7日間に350件以上等でGmail履歴検索が上限に達したら送信を停止する。
5. **送信できない理由の診断**: `diagnoseMateV4Backlog` を追加。件数をサービス別に、既送信／拒否・停止／業務メール欠落／窓口監査待ち／根拠期限切れ／証拠不足／公開メールレビュー不足／暫定適格に分類する。最後の暫定適格にはGmail履歴照合・実際の送信枠確認が含まれない。
6. **GAS再反映**: 既存GASのV4コードだけを最新版へ全置換して保存する。すでに本番送信がONなら `prepareMateDaily30V4` を再実行しない（OFFに切り替わるため）。`diagnoseMateV4Health` と `diagnoseMateV4Backlog` で設定と適格性を確認してから `mateAutoOpsV4Cycle` を実行する。
7. **公開/実稼働の区別**: GitHub `main` への反映は完了したが、Apps Scriptの本番配備・トリガー実行・新規営業送信数・候補の実増加はGitHubコミットだけでは証明できない。

## 運用上の注意
- 営業可能候補0件は送信枠の不足ではなく候補側の根拠、過去送信、拒否、メール不明などの条件による。根拠を確認できない相手に自動送信する仕様にはしない。
- 収集元CSVが現在PLAYに偏り、5ソースで新規0件という状況は、新しい公開データを無差別に増やしても改善しない。習い事・訪問保育など実際に営業対象となる事業者を含み、公式URLと再利用条件の確認ができたソースに限って追加する。
- 真の成果指標は内部テスト除外後の「実申請」「承認済み事業者」「営業起点の確認済み申請」。単純な名寄せは因果関係の証明にならない。
