## A. サービスのサイト構造

- MATE総合トップ: 事業全体の説明・各サービスのリンク・運営/プライバシー・問い合わせ（新ドメインのルート）。
- MATE CARE: シッター/育児サポート検索と掲載申請、家族向け相談（GAS受付の成功実績はPLAYのみ）。
- MATE SPARK: 習い事検索・比較、掲載申請。実在承認0件なら掲載準備中。デモ12件は `?demo=1` でのみ。
- MATE PLAY: 親子体験・外出検索、掲載申請、家族向け相談。元ChatGPT Sites CMSの完全移行は未完了。
- 検索/比較/お気に入りは会員登録なし。事業者の掲載申請と利用者の相談は別々のフォームと同意にする。
- 当面、予約完了・体験確約・料金の請求が自動で発生する画面は作らない。

## B. 推奨する独自ドメイン設計（購入前のサンプル）

まず**共通の1ドメイン**だけ取得する。下記は書式例であり、取得可能性や商標の調査は未完了。

| 用途 | URL例 | 役割 |
|---|---|---|
| ブランド総合 | `https://<BRAND_DOMAIN>/` | MATE総合の入り口 |
| CARE | `https://care.<BRAND_DOMAIN>/` | 育児サポート |
| SPARK | `https://spark.<BRAND_DOMAIN>/` | 習い事 |
| PLAY | `https://play.<BRAND_DOMAIN>/` | 親子おでかけ |

- `<BRAND_DOMAIN>` は候補名未確定。例：`kosodatemate.jp`、`mate-family.jp` 等（登録可否・商標・混同リスク未検証）。
- 4ドメインは不要。経営者/事業体が所有するレジストラアカウントで購入し、2FA、自動更新、期限通知、WHOIS情報の管理を実施。
- 日本国内中心なら .jp を優先候補。.com も予算/将来展開次第。**取得1年目の安さではなく更新費用**を比較。
- `https://www.j-platpat.inpit.go.jp/t0100` で商標の同一/類似サービスを調べてから購入。
- Firebase Hostingの各サイトは固有のドメイン・サブドメインを接続できる。DNSとSSL有効化は所有者が操作。DNS情報/秘密鍵を公開しない。
- SPARKはFirebase `mate-spark` 本番稼働。CAREは現状GitHub Pages、PLAYは元ChatGPT SitesとFirebase TESTが別。**PLAYのFirebase TESTに本番ドメインを割り当てない**。
- 移行時に各ページ単位で旧→新URLの対応表、canonical、sitemap、相対リンク、GA4のドメイン判定を更新。301転送ができるホストからの転送を優先し旧URLは維持。Google Search Consoleに新サイトマップ登録。
- 古い公開URLを切り替えるのは、新ドメインのSSL・フォーム本番疎通・モバイル表示を確認した後。ドメインだけ先に取得し、本番のDNS切替は段階的に実施。

## C. データ構造（3サービスの共通設計）

| レイヤー | 現状と整理方針 | 入れてはいけないもの |
|---|---|---|
| **営業候補** | 非公開Sheets「3サービス営業リスト」・窓口確認。照会日、営業拒否、担当、連絡状況を保持 | 推測だけで「掲載許諾済み」にすること |
| **申請** | 非公開Sheets「掲載セルフ申請」。サービス、掲載希望、情報確認日、公開ID、審査者等を持つ | 未審査なのに公開JSONへ流すこと |
| **契約/許諾** | 「掲載契約」で有効期限・同意者・条件版・証跡を別管理。掲載希望≠契約≠体験取次許諾 | 原文を公開JSONへ書き込むこと |
| **家族相談** | GAS→運営用Gmailに本文・返信先→「問い合わせ管理」に受付番号・ステータスのみ | 顧客メール、子の氏名、電話、相談本文を公開JSONへ流すこと |
| **公開** | `service/id/name/region/category/price/age/website/verifiedAt` など公開可能フィールドだけを独立JSONへ生成 | 非公開の担当者連絡先、審査メモ、メールID、デモと実在の混在 |
| **収益** | 当面は別の月次仮説表。将来、契約ID/サービス/期間/成果ID/成果確認日/請求ID/入金日/返金を分離 | 「フォーム送信試行」を売上や予約成立と数えること |

データIDはCARE/SPARK/PLAYを正規の列挙値とする。旧SITTERはCAREに対応するレガシー表記として互換変換し、既存の記録は断りなく破壊しない。レイヤー間の自動同期は**厳格な承認・署名・同意・有効期限の条件を全て満たしたときのみ**。同一申請の受付番号で重複処理しない。プロダクションとテストFirebaseの環境を分離する。

## D. 営業を始めるための順序

### 無料掲載の営業「GO」条件
1. ブランド独自ドメインを1つ選んで購入。送信用文面が新URLへ遷移できること（取得のみ先行でもよいがサイト案内は実在するページのみ）。
2. CARE/ SPARK / PLAYの既存掲載申請リンクが利用可能で、事業者の入力は公開承認前に審査保留になること。CARE/PLAYの家族相談はGAS。PLAY本体の公開CMSを手動で編集する場合は自動掲載と宣伝しない。
3. 送信元アカウント・差出人表示・送信者住所または適切な営業案内URLと停止希望対応を確認。事業として必要な表示を準備。育休中の事業稼働/兼業規程/給付の扱いを確認。
4. 「MATE_初回営業10件」から最初の会社の公式サイト・窓口用途・営業拒否/過去接触を再確認し、**本人が文面を確認して1件送信**。古い確認日時を自動的に最新扱いにしない。
5. 運営Gmail→回答→掲載権限検証→原稿・画像利用許諾→先方による内容確認→審査者が承認して初めて公開。ユーザー本人の個人情報を勝手に事業者へ取次しない。

### 営業で検証する最低KPI
- 窓口の再確認数 / 発信数 / 返信数 / 相談数 / 掲載許諾獲得数 / 公開済み件数 / 家族からの有効相談数 / 実際の取次合意数 / 成約確認数。
- 初回は **CARE4・SPARK4・PLAY2** の10先。サービス別の反応・掲載までの工数を比較する。送信承認や自動送信は全件OFFのまま。
- 「サイト訪問数」「ボタンクリック」「相談の送信試行」「GASが返した受付番号」「事業者が確認した成果」を別の指標として管理。GA4には個人情報を送らない。

既存の「月次収支シミュレーション」に加え、非公開CRMに「MATE_3サービス収益モデル」を作成。全て仮説、実績収益ではない。

| 商品 | 初期提案 | 有料検証の候補（価格は未確定） | 条件 |
|---|---|---|---|
| 共通：無料掲載 | 月額0円、初期費用0円 | 無料掲載を維持 | 先方から掲載権限と原稿許諾を取得 |
| CARE | 掲載＋比較・相談 | 月額11,000円 or 成果3,300円/件 | 成果の定義・提供業務・料率/単価・キャンセルを別途合意 |
| SPARK | 掲載＋比較 | 月額5,500円 or 成果1,650円/件 | 体験の受付に両当事者の取次許諾が必要 |

- 初期は有料課金より**掲載・紹介の効果が確認できる状態を先につくる**。掲載0件・利用実績0件のまま有料契約の自動請求を始めない。
- 将来の請求には正式な有料契約、成果ログ、返金・キャンセル、消費税、請求書・入金管理、規約や法令表示の確認が必要。
- シミュレーション例（2026-10-28）：保守 売上93,500円 / 人件費後-64,000円、標準 売上313,500円 / 人件費後43,500円、拡大 売上698,500円 / 人件費後214,500円。実績や売上予測ではなく、単価・件数の仮説。
